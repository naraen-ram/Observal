## Hook setup and delivery

- The reviewed Observal `doctor patch --harness codex` commands at `UserPromptSubmit` and `Stop` invoked only the isolated installed Python module `observal_cli.hooks.session_push --harness codex`. The native feature list showed `hooks = true`. Through the native `/hooks` CLI UI, we reviewed and trusted those two definitions; after restarting Codex, `/hooks` opened without another trust prompt. **Trust was persisted, not bypassed.** These hooks deliver sessions; they are not evidence of an unrelated registry hook component executing.
- The previous doctor emitted a top-level `codex_hooks = true`. Codex 0.163.0 warned in actual `codex exec` stderr that the root key **is ignored**. The scratch profile also had the effective `[features] hooks = true`, explaining why it worked despite that warning. The CLI doctor fix now writes/diagnoses the canonical feature, removes its unadorned old root key, preflights existing TOML before touching hook files, preserves unrelated tables, and explicitly directs the operator to review `/hooks`. A separate temporary migration control showed native `codex doctor` config-load status `ok`, native feature enabled, and two managed events. This does **not** programmatically grant trust or prove a user's normal home is configured.
- A new no-tool `codex exec` session completed with native `UserPromptSubmit` and `Stop` hook completions, then appeared with 14 lines in the **loopback warehouse before reconcile**. Another no-tool run after reviewing five additional scratch-only diagnostic hook definitions wrote a mode-0600 journal with `SessionStart`, `UserPromptSubmit` and `Stop` entries. The journal stored only event names, bounded timestamps, fixed tool kind, allowed-read boolean and hashes of session/call IDs; it never stored hook stdin, prompts, command text, tool input/output or provider payload. A real-provider manual read fired paired `PreToolUse` and `PostToolUse` for its one allowlisted, inert skill file. This diagnostic journal was not uploaded as component-use evidence.
- Eleven completed controls and two unsuccessful provider controls generated 13 native session files, all with a loopback warehouse checkpoint **before any reconcile**. One provider launch lacked a private bridge dependency and timed out; another used an unavailable test model and returned 404. Neither is a completed no-tool or invocation acceptance session. The later real-provider controls used the previously tested same-account Azure Responses route via a loopback-only pass-through; the Codex child did not receive the Azure credential, and the bridge persisted no request/response bodies. Scratch `PreToolUse` denied all tools except an exact read-only command for the inert file; the native `read-only` sandbox was also enabled.

## New candidate: native skill-selection provenance

In this exact Codex build, the persisted native `response_item` user message has `internal_chat_message_metadata_passthrough.content_item_kinds`. Its **controlled native skill expansion** carries `skills.selected_skill_instructions`, and the adjacent expansion text names the absolute project `SKILL.md` location. The preceding user's prompt is `user.text`. One prompt selecting both inert skills produced **two separately tagged expansion records** in the same turn. A real-provider explicit selection and scripted-provider selections showed the same metadata kind. A plain name mention (scripted and real-provider), an unknown `$name`, and a pasted `<skill ...>` imitation produced only `user.text`; a real-provider *manual read* likewise had no selected-skill tag, instead producing a linked `custom_tool_call` and `custom_tool_call_output`. These controls correct the earlier assumption that the native rollout records only indistinguishable text. A copied expansion body is still not enough; the native metadata is the candidate origin discriminator.

**No new evidence cell was enabled in this discovery workspace.** The new scratch workspace lacks a contemporaneous tracked registry skill receipt, and neither the source-version bump, fail-closed extractor, repeated/shadowed-skill negatives, immutable projection/replay nor matched/unmatched API/CLI/worker/browser reporting has been performed. A future extractor must require this exact native kind, one valid same-turn project location and a unique verified install, reject malformed/duplicated/spoofed/reordered or other-version sources, and never publish expansion content. Skill *load* remains unproved; an arbitrary file read is not a load signal.
