# Component Insights harness matrix: Codex skill evidence and bounded MCP calls

This work is **stacked on draft #1779**, not a replacement for its verified-only installation contract. [Current status](component-insights-matrix-roadmap.md) and the [remaining per-cell evidence gates and estimates](component-insights-remaining-harness-gates.md) are tracked separately. Discovery used temporary harness homes and an isolated loopback-only Compose project. No historical installation was inferred from current configuration, a transcript tool name, a skill mention, an Agent pin, or a manual reconcile. Raw sessions, credentials, arguments, prompts and provider responses are not fixtures or PR artifacts.

Only the exact recorded Codex version and POSIX absolute-path inventory are accepted; Windows paths remain unsupported until independently recorded. Missing or multiple native inventories, mismatched or repeated roots, repeated aliases, other project roots, home/ancestor skills, version changes, drifted/unverified pins, and mapping collisions never become attributed availability. A session on an untested version returns `unsupported`, not zero. No new hook cell is opted in; the MCP cell is limited to the exact Codex version, native completed call shape and verified installation. The developer inventory format and Mac `/private/tmp` canonical path variant are covered by sanitized fixtures; `tests/test_codex_skill_evidence.py` checks the verifier and same-hash matcher independently. The skill summary separates **availability** from the **use** denominator. In the *original availability-only, version-3 cohort*, `offered: 1` accompanied null loads/invocations and no use denominator. Its isolated version-scoped report had 7 verified-present/available sessions, 3 invocations and denominator 7; shadow and drift were excluded. Missing or unsupported native provenance is unknown, not a zero-use session. Other scopes and versions remain unsupported.

## Other runtimes and originally unproven signals

- **Kiro IDE 1.3.11:** A real connected, **manually configured** user-scope inert MCP did execute `ping`; the native tool result contained the inert pong and an independent scratch marker confirmed execution. That configuration was **not** an Observal tracked install. Two subsequent IDE sessions (including the user's trust-and-chat control) were created with the standalone hook file under the project's `.kiro/hooks/`. The IDE registered all four hooks, but neither a prompt nor a silent post-tool marker appeared; both sessions were absent from Observal **before** manual recovery. A dry-run showed `2 would_push`, `4 up_to_date`; manual reconcile pushed the two without error. The isolated warehouse then had six IDE sessions / 87 events. This proves a parser and manual recovery, not automatic IDE delivery or a verified-present denominator. Earlier standalone user-home placement was incorrect for the IDE and was disabled; fixing that placement did **not** establish execution. Kiro CLI 2.32.0 is a separate runtime sharing the `kiro` registry key, so IDE-only evidence cannot safely make CLI sessions measurable.
- **Kiro CLI 2.32.0:** Real `ping` execution and a silent independent hook marker were observed in separate controls, but the transcript did not supply attributable MCP-install identity or per-hook execution identity. The tested standalone v1 hook did not fire on CLI 2.x. No verified MCP-use cell.
- **Cursor Agent 2026.10.14:** Real accepted and rejected inert MCP attempts, skill-file reads and name mentions were controlled. MCP success/pong was in the live stream, **not** persisted JSONL; the persisted attempt cannot distinguish denial from success. A file read is not a native skill-invocation identity. Original temporary delivery hooks sent four sessions, but did not record attributable component hook runs. No MCP/skill/hook *use* cell opted in.
- **Codex hooks (original discovery):** Real provider sessions and vetted temporary hook markers demonstrated session delivery, but originally an executed tracked MCP `ping` was not established; the follow-up above closes that *MCP* gap only. A printed hook marker and a native developer-message output do not establish a registry hook's attributable execution identity. The later [isolated Codex hook/skill follow-up](component-insights-codex-hook-skill-followup.md) found a native selected-skill metadata kind that distinguishes the controlled `$skill` expansion from pasted imitation text and manual reads. The earlier discovery had no tracked receipt; the [subsequent verified project-skill follow-up](component-insights-codex-skill-verified-followup.md) implements the narrowly version-scoped invocation cell. Skill loads and registry-hook execution remain unsupported.

The stacked follow-up now permits stdio-only tracked MCP `--apply` on tested Kiro CLI 2.32.0, Codex CLI 0.163.0, and Cursor Agent 2026.10.14, subject to native configuration, shadow, trust, version, drift, and privacy checks. Real registry installs in isolated homes were pinned and verified; no-tool sessions from all three harnesses automatically reached the loopback warehouse without reconcile. A second Cursor control required an adapter fix to recover the *single native workspace root* from its headless `sessionEnd` payload: the first Cursor session reached the warehouse without its project pin and remains unattributed, whereas the corrected follow-up carried a canonical verified snapshot. Kiro and Cursor subsequently executed an inert approved `ping` with independent scratch markers and automatic delivery, but Kiro persisted only the generic name `ping`, and Cursor's persisted JSONL still omitted the success status. Codex's scripted and real-provider follow-ups recorded a server-named `McpToolCall` only after an explicit scratch-only approval. A **Codex CLI 0.163.0** native `item_completed` MCP extractor now permits an attributable call only with its native server, tool, ID, timestamp, completed status and boolean `result.isError`, alongside a uniquely verified v2 pin. Denied approvals (`failed` with no result), interrupted calls, malformed/duplicated records and other versions remain **unsupported**, not zero; native user messages and synthetic function calls are not evidence. A loopback scripted provider reproduced project- and user-scope approved executions with independent server markers; an additional real-provider project run independently confirmed the native shape. Automatic hooks delivered the new sessions without reconcile using temporary, trusted/bypassed hook settings, and current-version warehouse projections published exact `verified_server` successes in both scopes. A worker-generated **version-scoped** live report after both runs showed 20 verified-present sessions across harnesses, 4 successful calls, and a usage denominator of 11; 6 unsupported-harness and 3 pending sessions remain explicitly excluded (not zero). CLI JSON, desktop/mobile browser checks and privacy-preserving screenshots under `/tmp/component-matrix-probe/` agree. These are conditional mixed-cohort figures, **not** a claim that all 20 sessions or all harnesses are measured. Cursor requires separate per-session MCP approval. HTTP/extra options, Kiro IDE identity and untested versions remain unsupported. Manual scratch MCP entries and an Agent pin alone still cannot supply a verified denominator. Kiro IDE and CLI need distinct capability/projection handling before opting in IDE-only cells. Unsupported evidence is **unknown**, never success, failure or measured zero.

## Additional bounded feasibility controls

A later isolated Kiro CLI 2.32.0 **inline v2-agent** hook probe resolved the previously missing *hook-side* server identity. `preToolUse` received native `tool_name: @matrix-mcp-probe/ping` on both an approved and a denied attempt; `postToolUse` fired only after the approved, executed call. The approved call also wrote the independent inert server marker and its native session contained a successful `toolResult`; the denied controls' native result was `error`. A no-tool session fired neither tool hook. The fresh approved/no-tool sessions automatically arrived on the loopback stack with the same verified MCP mapping before reconcile. A further **two-server/same-`ping`** control placed a separately marked, untracked alias beside the verified project pin. Its independent marker and pre/post hooks agreed on `@matrix-mcp-collision/ping`; the automatically delivered session still mapped the *other*, tracked alias as verified. This demonstrates hook-side server selection, **not** attribution of the untracked execution to that pin. **This does not enable Kiro MCP-use reporting:** the session JSONL still names only `ping`, hook stdin is not a durable canonical source, the hook has no tool-use ID or result status, and a missing hook invocation does not prove no use. The scratch agent exposed only the two inert MCPs; `--trust-all-tools` was used only for the isolated noninteractive controls, not as a production setting. Scratch hook records retained only structural keys, alias and a session digest. Additional aliases and tool-probe hooks were removed from temporary profiles after testing.

**Cursor Agent 2026.10.14-941492e was subsequently authenticated in its isolated home**, using the CLI's file credential store rather than the ordinary macOS keychain. The installed build actually fired native `beforeMCPExecution`/`afterMCPExecution` hooks: both named the server and tool and shared `session_id` and `tool_use_id`. An unapproved call had `rejected: true` and no server marker; an approved `ping` produced a distinct marker and `isError: false`; an inert failing MCP tool wrote its own marker and returned `isError: true`. The generic `postToolUse` fired even for rejection/error, so it cannot stand in for a successful result. Two servers exporting the same `ping` wrote different markers and were distinguished by the hooks' server field despite identical native JSONL attempt names. Fresh project no-tool/accepted/denied/error/collision and user-scope accepted sessions automatically delivered with verified mappings. An initial user-scope hook spooled because a *temporary Observal* access token was expired; only a fresh-token run is counted as user-scope automatic acceptance. Scratch probes saved **no** hook stdin, result body, arguments, prompts or email; they retained only structural keys, strict result flags and one-way session/call digests. The extra MCP aliases and probe hooks were removed, preserving the original session-delivery hook. **That initial native probe alone enabled no Cursor MCP-use cell.** A further **local-only CLI collector** now writes a bounded private journal of tested-version `sessionStart`, before/after MCP and `sessionEnd` events; it hashes the authenticated user, exact native source and managed hook config, pairs one-way call IDs, checks the native `CallDynamicTool` count, and appends only validated sanitized lines through the existing acknowledged session push. The hook command returns `{}` and does not grant tool permission. The tested `sessionStart` lacks an absolute transcript path, so the collector uses one native project root plus session ID to bind its expected JSONL location, requiring exact subsequent path agreement. Fresh project no-tool, approved, rejected and inert server-error sessions, plus a user-scoped approved call, arrived before reconcile with sanitized rows and verified mappings. A two-server/same-`ping` control emitted the untracked alias's own source record while the other alias remained the only verified pin; a first scratch snapshot was pending when its native config was restored before asynchronous upload, so a second control held the config until mapping completed. No result body, tool input, prompt, email or raw hook stdin entered the journal or its uploaded source lines. **Cursor still has no server-side invocation extractor or published use denominator**; client-side completeness checks are not an independent warehouse projection or proof of universal hook coverage. Kiro IDE's earlier isolated log recorded `hooks.v2.executionDisabledUntrustedWorkspace`; later trust alone did not establish hook execution. See [remaining gates](component-insights-remaining-harness-gates.md) for the independent extractor, privacy and no-tool coverage requirements.
